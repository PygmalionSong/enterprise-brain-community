# Native enterprise database adoption

[中文](NATIVE_DEPLOYMENT.md) · [Connection prerequisites](NATIVE_RUNTIME.en.md) · [Session ownership](NATIVE_OWNERSHIP.en.md)

The trusted local `adoptNativeEnterprise(root, configFile, inputFile)` programmatic interface adopts a dedicated PostgreSQL enterprise database already migrated, granted and initialized by the customer's DBA. It never migrates, grants, creates accounts or changes business rows, budgets or model installations. Dedicated-database acknowledgement is an explicit DBA assertion; one RLS-visible enterprise parent does not establish a complete database inventory.

`configFile` must be `config.json` inside a new dedicated child directory of an existing canonical private parent. Existing targets, indirect paths, device aliases and hidden settings directories are refused. Strict private input JSON contains `enterpriseId`, `runtimeRole`, canonical HTTPS `origin`, backend `port`, absolute `runtimeDescriptorFile`, exact64-character lowercase `runtimeDescriptorSha256`, and explicit `adoptionAcknowledged: true` / `dedicatedDatabaseAcknowledged: true`. Keep inputs, descriptors, credentials and configurations out of repositories.

The connection core hashes and parses the same bounded descriptor bytes before reading password/CA references. Verified native account/TLS provenance must match enterprise, role and descriptor SHA. Adoption rechecks migrations, account/workload privileges and an effective identity administrator, then retains dedicated database session ownership. Any model installation or enabled graph delegation refuses adoption without reading its credentials, calling models/tools, silently uninstalling or disabling it. Operators must handle these through the existing controlled interfaces first.

Success publishes only independent `format: 2, storage: "postgres"` configuration, random private proxy/control tokens and a `parked` version0 traffic policy. It opens no listener or background pump. Absolute paths bind the final directory; tokens are separate files, never printed or embedded in descriptors. A target-bound cooperative claim and private sibling staging directory prevent concurrent cooperating adopters from committing together; database ownership is retained through publication. Failures retain the claim and any stage for inspection, never steal old claims, overwrite existing directories or recursively remove unknown paths. Inspect target/claim/stage before retrying or removing owned files after an uncertain result. This is not malicious-local-admin or power-loss durability certification.

`readNativeDeployment` validates fixed private paths, tokens and current descriptor SHA for startup. `readNativeControlDeployment` validates local configuration/fixed paths/tokens for identifying and stopping the original instance; a changed or missing descriptor does not block that read and cannot authorize a new connection. Shared operation locks hash the entire actual configuration, including native role/descriptor SHA. Password/CA rotation still requires explicit stop/reconnect; descriptor SHA neither proves referenced files unchanged nor establishes that new credentials took effect.

Original `format: 1` PGlite readers, file backups and upgrades refuse this format. Never back up external PostgreSQL with local file copying. Separate local contracts cover [native hosting](NATIVE_SERVICE.en.md),[daily model/tools](NATIVE_AGENT_CONFIGURATION.en.md),[encrypted backup/quarantined restore](NATIVE_BACKUP_RESTORE.en.md) and [new empty-database DBA preparation](NATIVE_DBA_PREPARATION.en.md). DBA preparation is an explicit separate command and preserves read-only adoption. Native cross-version upgrades and HA remain separate work. Owned Windows/PG17/TLS verification does not qualify clean hosts, Linux, production certificates or real customer environments; live models and public release retain separate boundaries.
